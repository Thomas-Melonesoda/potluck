# Resume storage

Pause and pickup share one locator: the task's folder, plus a task name when one folder holds more than one task. The `resume.mjs` command under `skills/poteto-mode/scripts/` keeps checkpoints in a store with one pointer per folder and task, so several projects in one repository or vault, or several tasks in one folder, never overwrite each other's pointer. Each pointer records the folder, task, worktree, branch, HEAD, timestamp, note, and requested artifacts with content hashes.

- In a Git checkout the store is `pstack/resume/` under the project's Git common directory. Git worktrees of the same repository share it, Git excludes its contents from commits, and a folder is named by its path inside the worktree, so the same folder in another worktree finds the same pointer.
- A folder outside Git keeps its store in `.pstack/resume/` inside the folder.
- `--store <directory>` puts the store at a location you name instead, such as a notes folder that outlives the project. Several folders can share one store. Pass the same `--store` to every command for that checkpoint.

Claude Code, Codex, and other runtimes use this same command and location. Runtime-specific home directories and transcript encodings do not affect lookup. The default store does not survive deleting or recloning the repository, or deleting the plain folder; before that happens, transfer the complete checkpoint to durable storage or a `--store` location and give the resumed session its locator.

## Write a checkpoint

`--project` is the task's folder: the worktree for code, or a project's own folder inside a larger repository or vault. Add `--task <name>` when another task may checkpoint in the same folder, such as a second session in the same checkout or in another worktree of the repository (their top folders share one pointer), or when the user named the task. Use a name of letters, digits, `.`, `_`, and `-`; Copilot asks before it runs a command with any other name. Pass the same `--project`, `--task`, and `--store` to every command below (`begin` takes no `--task`).

1. Run `node <scripts>/resume.mjs begin --project <folder>` to allocate a new checkpoint directory. Write `resume.md` there with intent, verified progress, current state, and next steps.
2. Save requested artifacts in that directory and link them from the note. Reuse existing artifacts in the project when their location survives the anticipated interruption. Do not make competing copies. For a worktree that will be removed, place the requested material in the common checkpoint store instead. Check exact wording, completeness, and order where required.
3. Publish with `node <scripts>/resume.mjs publish --project <folder> --note <resume.md> --artifact <file> ...`. Register every local note link as an artifact, including existing project files. Link each local file with an inline Markdown link whose destination is the path, written bare or as `<path>`, with no square brackets in the link text and no title after the path. Reference-style links are not read. The path is relative to the note or absolute, and it is percent-decoded, so write a literal `%` as `%25`. Wrap a path that contains spaces or parentheses in angle brackets, or percent-encode it. Links inside code spans and fenced code blocks are ignored. Each rejected link reports this rule. The command verifies file ownership, links, and contents, records HEAD, and then atomically replaces the pointer for that folder and task. A failed publication must not be treated as a ready checkpoint.
4. Run `node <scripts>/resume.mjs read --project <folder>` and open its note and artifacts. Treat published checkpoint files as immutable. Use a new checkpoint directory for a later pause. If an existing project artifact changes, pickup reports that difference rather than silently treating it as the saved material.

`begin` separates concurrent writers' files. Publishing replaces one pointer per folder and task atomically; the last complete publication for that pair wins, and every other folder and task keeps its own. The pointer is a locator, not a task scheduler or execution lock.

## Read a checkpoint

Session pickup starts with `node <scripts>/resume.mjs read --project <folder>`, adding `--task` when the user named one. Exit 0 with `kind: checkpoint` provides the saved note and all registered artifacts. Open them before searching transcripts. The command validates hashes and links again, including reuse of project artifacts.

The same output compares heads. `checkpoint.head` is HEAD when the checkpoint was published. `headNow` is the saved branch's tip now, or this checkout's HEAD when the pause was on a detached HEAD. `moved: true` means the saved branch changed after the pause: commits landed, the branch was reset, or, with `headNow: null`, it was deleted. Read `git log <head>..<headNow>` when both exist, or find where the branch went, and recheck the note's claims against that change before trusting it. `moved: null` means there is no recorded head to compare, as in a folder outside Git.

Exit 2 with `kind: missing` means no pointer for that folder and task. Run `node <scripts>/resume.mjs list --project <folder>` next. It lists every checkpoint in the store, newest first, with its folder and task, so a checkpoint saved for another folder of the repository or under a task name is still found. A folder outside Git has a store of its own, so its `list` shows only its own checkpoints, unless several folders share a `--store`. Read the one that matches the user's request with its own `--project` and `--task`. Only when nothing matches, use the transcript, cloud URL, or branch fallback. A checkpoint in the earlier single-pointer format (`latest.json` in a Git store), which an older plugin may still write, reads as the top folder's checkpoint with no task. When both exist, the newer wins, and publishing the top folder retires `latest.json`.

Exit 1 with `kind: unavailable` means a checkpoint is malformed, unreadable, changed, or incomplete. Diagnose that concrete gap; do not silently ignore the checkpoint or claim the material was never saved. None of these commands causes a running task to pause.
