# 用 potluck 时项目需要哪些文档

[English](project-docs.md) | **中文**

当大部分工作由 agent 来做时，这份指南说明项目需要哪些文档、各由谁写、怎样保持真实。它取代"写代码之前先手写需求文档、架构文档、测试计划和待办清单"的做法。在 potluck 里，这些内容大多由 **grill** 向你问出来，或由检查守住，或自动生成。

背后的原则是：agent 无法检查的文档会慢慢失真。所以每个事实只放在一个主来源里，由人来定，agent 能检查；任何汇总这些来源的东西，都从来源生成。

## 主来源

只有下面这些是手工维护、描述项目本身的文档。功能文件、术语表、质量约定、决定记录和裁定，由 **grill** 在开工前和你一起写出；其余的由 agent 按项目的实际情况写。之后 agent 随工作变化让它们都保持最新。

| 主来源 | 回答什么 | 谁写 | 怎样保持真实 |
| --- | --- | --- | --- |
| `README.md` | 这是什么，怎么运行 | agent，按项目实际命令写 | 写进去的命令都先实际跑过 |
| `AGENTS.md` | agent 在这里该怎么工作 | 你和 agent；改它永远由你决定 | 各工具都读它（`CLAUDE.md` 里只有一行 `@AGENTS.md`） |
| `docs/features/<功能>.md` | 每个功能是什么、给谁用、做到什么算完成 | **grill**，按你的回答写 | "完成条件"只有附上证据才能打勾；只打勾不附证据，总览检查会拒绝 |
| `GLOSSARY.md` | 项目里的词各是什么意思 | **grill** 和 **domain-modeling** | 用词和它冲突时立即指出 |
| `CONSTRAINTS.md` | 做到多好才算够好 | **grill** 和 **constraint-driven-development** | 每条强制规则都写明由哪个命令判定；质量底线检查会拒绝放宽它的改动 |
| `docs/adr/NNNN-<标题>.md` | 一个不容易改回去的选择为什么这样做 | agent，只在 **domain-modeling** 的三个条件都满足时写 | 被取代的记录标出来，不删改 |
| `docs/rulings.md` | 你做过的决定，用你自己的话 | **grill**；之后你在对话里做的决定，你要求时按同样方式加进去 | 每条都有日期、问题和你的原话 |
| 使用说明（README 的一节，或 `docs/user-guide.md`） | 人怎样完成实际任务 | agent，在功能能用之后写 | 步骤对照运行中的程序检查过 |

可选：很长的原始讨论（导出的对话、草图、截图）放进 `docs/background/`，用来追溯某个决定的由来。它从来不是规则；和主来源冲突时，以主来源为准。

## 自动生成的内容

| 文件 | 从哪里来 | 怎样保持最新 |
| --- | --- | --- |
| `docs/overview.md` | 功能文件、`GLOSSARY.md`、`CONSTRAINTS.md`、ADR、裁定，以及 README 的标题和第一段（项目有功能文件之后） | 任何改动主来源的提交都用 `grill/scripts/overview.mjs --write` 重新生成；总览过期的 PR，质量底线检查会拒绝；没有功能文件的项目没有总览 |
| 某个功能的状态图 | 功能状态的模型，由 **statechart** 对照规则检查 | 改动碰到这个功能的状态逻辑时，自动附在回复里 |
| 长时间运行的决定记录 | 运行本身，经由 **show-me-your-work** | 边运行边写 |

## 起步文件

grill 结束时，`grill/scripts/starter.mjs` 补上项目缺的文件。已有的文件一律不覆盖，所以重复运行也安全。

| 文件 | 作用 |
| --- | --- |
| `.github/workflows/ci.yml` | 每个合并请求和默认分支上都跑项目那一条检查命令。命令还没定时，这一步失败并说明原因 |
| `.githooks/pre-commit` | 每次提交前跑 **constraint-driven-development** 的质量底线和 gitleaks 密钥扫描。起步脚本在这份克隆里启用它，并把底线检查放在克隆的 git 文件夹里，不放进代码树 |
| `AGENTS.md`，以及内容为 `@AGENTS.md` 的 `CLAUDE.md` | 项目给 agent 的说明的骨架。agent 按 grill 定下的决定填写，没定的地方留着"to confirm" |

## 不再手写的文档

| 旧文档 | 由什么取代 |
| --- | --- |
| 手写的需求文档（PRD） | 功能文件、`GLOSSARY.md`、`CONSTRAINTS.md` 和 `docs/rulings.md`，由自动生成的总览汇总 |
| `docs/architecture.md` | **architect** 在写代码前定下的设计，加上需要记录的 ADR |
| `docs/TEST_PLAN.md` | 每个功能的完成条件、项目的验证 skill（由 **create-verification-skill** 生成），以及 `CONSTRAINTS.md` 里的检查 |
| 作为状态主来源的 `TODO.md` | 已打勾和未完成的完成条件，在总览里统计；长时间运行时，用 playbook 的任务清单和决定记录 |

已经在用其中某个文件的老项目可以继续用，但它不能再放主来源里也有的事实，而是链接到主来源。

## 范围：grill 问的问题

新项目或意图不清的大功能开始前，**grill** 只问人能回答的问题。每个问题都带推荐答案和默认值，所以回答"不知道"也能得到一个可用的决定。

| 问 | 为了弄清 |
| --- | --- |
| 做什么 | 第一版有哪些功能，哪些暂不做（例如登录、付款、自动发送任何东西） |
| 给谁用 | 谁在用、分哪些角色、要完成什么任务 |
| 怎样算完成 | 你看到什么就知道它能用了，包括出错时应该发生什么 |
| 什么算错 | 什么情况你会说它坏了、不安全、太慢或太贵 |

第一版到哪里为止也属于"怎样算完成"：能演示、自己日常用、给别人试用，还是公开上线。每种的答案不同，所以先定这一项。

技术问题（数据结构、模块、用什么库）不问人，写进功能文件留给 **architect**。只有试过才能回答的问题，交给 **prototype**。

## 追问分支

项目有下面某种情况时，**grill** 会追问对应的问题，答案写进功能文件的完成条件，或成为 `CONSTRAINTS.md` 的一行。

| 项目有 | grill 追问 | 写到哪里 |
| --- | --- | --- |
| 页面或多个操作步骤 | 主流程上的空数据、加载中和失败时的样子 | 完成条件 |
| 要保存的数据 | 存什么、怎样变化、怎样删除和恢复 | 完成条件；存储方式的选择写 ADR |
| 分开开发的部分（前后端、多个模块） | 每一边可以对另一边做哪些假设 | 完成条件；接口契约测试写进 CONSTRAINTS |
| 登录、角色、私人数据或文件上传 | 谁能看到什么、密钥放在哪里、记录哪些日志 | 完成条件；密钥扫描和依赖扫描写进 CONSTRAINTS |
| AI 问答、识别或排序 | 样本输入、什么算对、质量门槛、成本和速度 | 一组评测样本；通过率和预算写进 CONSTRAINTS |
| AI 使用文档资料 | 用哪些来源、冲突时以哪个版本为准、回答怎样注明出处 | 完成条件 |
| 自动发消息、定时任务或有副作用的调用 | 重复执行、失败重试、何时停止、谁能批准 | 完成条件；不能撤销的动作仍然要停下来等人 |
| 需要一直在线的服务 | 部署、健康检查、回滚、备份 | 完成条件；发布前要跑的检查写进 CONSTRAINTS |
| 付款或订阅 | 订单状态、重复回调、退款、测试模式 | 完成条件 |
| 支持多个系统、浏览器或设备 | 支持哪些、哪些版本 | 测试组合写进 CONSTRAINTS |
| 一项核心能力能不能做到还不知道 | 能回答这个问题的最小实验 | 用完即弃的实验放在单独的分支；结论写进 ADR 或 `docs/rulings.md` |

## 书写要求

无论是否自动生成，每份文档都要遵守。

**真实性**

- 计划和结果分开写。计划写"打算怎样检查"；结果写"实际跑了什么、是否通过、哪些没检查"。没有实际运行，就不写"已通过"。
- 没人验证过的判断标为"未验证"，不把猜测写成事实。
- 写绝对日期（2026-10-20），不写"昨天""下周"。

**读者和结构**

- 读者是不写代码的人和 agent。用通俗的话；专业术语第一次出现时解释一句。
- 结论先行，再写理由。比较多个选项时用表格，写出代价和为什么选这一个。
- 一份文档只做一件事。一个事实只在它的主来源写一次，其他地方链接过去。
- 写具体。"支持关于文档的问答"太宽泛，没法检查；"文档覆盖的问题给出回答并链接到原文，没覆盖的问题提示去问人"可以原样变成完成条件。

**链接和路径**

- 项目文档之间用相对路径链接。不要把自己电脑上的路径写进项目文档，项目一挪地方链接就失效。

**多个 agent 协作**

- `AGENTS.md` 是唯一的规则文件。其他工具的文件（例如 `CLAUDE.md`）只指向它。
- 接手的 agent 先读 `AGENTS.md` 和总览，再拿代码、版本和检查结果来核对。需要延续的东西不能只存在某个 agent 的记忆里：决定写进主来源。
- 文档对"哪个 agent 做什么"保持中立，除非你确实这样分工。

## 出现变化时

| 变化 | 更新哪里 |
| --- | --- |
| 新功能，或流程、完成标准变了 | 对应的功能文件（并重新生成总览） |
| 新词，或一个词被用成了两种意思 | `GLOSSARY.md` |
| 质量门槛变了 | `CONSTRAINTS.md`。agent 可以收紧；放宽它的改动会被质量底线检查拒绝，所以放宽只能由你自己改、自己合并 |
| 一个不容易改回去的技术选择 | 新的 ADR；旧的标为已取代 |
| 你在对话里做的决定 | `docs/rulings.md`，你的原话和日期 |
| 启动、配置或发布的方法变了 | `README.md` |
| 人要做的操作步骤变了 | 使用说明 |

过时的文档要么更新，要么在顶部标明已被哪份文档取代，不留下两个互相矛盾的版本。需求和取舍由你决定，agent 可以起草；每一句"它能用"都要有实际运行作为依据。
