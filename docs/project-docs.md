# Project documents with potluck

**English** | [中文](project-docs.zh-CN.md)

This guide says which documents a project needs when agents do most of the work, who writes each one, and how they stay true. It replaces the habit of hand-writing a requirements document, an architecture document, a test plan, and a to-do list before coding. In potluck, most of that is either asked for by **grill**, kept by a check, or generated.

The rule behind it: a document an agent cannot check drifts. So each fact lives in one source that a person decides and an agent can test, and anything that summarizes those sources is generated from them.

## The sources

These are the only hand-maintained documents about what the project is. **grill** writes the feature files, glossary, constraints, decision records, and rulings with you before building starts; agents write the rest from the project's real state, and keep all of them current as the work changes.

| Source | Answers | Written by | How it stays true |
| --- | --- | --- | --- |
| `README.md` | What this is and how to run it | An agent, from the project's real commands | Commands in it are run before they are written down |
| `AGENTS.md` | How agents should work here | You and an agent; editing it is always your call | Each harness reads it (`CLAUDE.md` holds only `@AGENTS.md`) |
| `docs/features/<feature>.md` | What each feature is, who it is for, and when it is done | **grill**, from your answers | A Done when item is ticked only with its proof; the overview check refuses a bare tick |
| `GLOSSARY.md` | What the project's words mean | **grill** and **domain-modeling** | A term that clashes with it is raised at once |
| `CONSTRAINTS.md` | How good is good enough | **grill** and **constraint-driven-development** | Every enforced rule names its command; the merge gate's floor refuses a change that weakens it |
| `docs/adr/NNNN-<slug>.md` | Why a hard-to-reverse choice was made | An agent, only when **domain-modeling**'s three conditions hold | Superseded records are marked, never edited away |
| `docs/rulings.md` | What you decided, in your words | **grill**; a later decision you make in conversation is added the same way when you ask for it | Each entry has the date, the question, and your answer verbatim |
| A user guide (a README section or `docs/user-guide.md`) | How a person gets a real task done | An agent, once a feature works | Steps are checked against the running app |

Optional: keep long raw discussions (exported chats, sketches, screenshots) in `docs/background/` for tracing a decision back. It is never a rule; when it disagrees with a source, the source wins.

## What is generated

| File | From | How it stays fresh |
| --- | --- | --- |
| `docs/overview.md` | The feature files, `GLOSSARY.md`, `CONSTRAINTS.md`, the ADRs, the rulings, and the README's title and first paragraph, once the project has feature files | Regenerated by `grill/scripts/overview.mjs --write` in any change to a source; the merge gate refuses a PR whose overview is stale; a project without feature files has none |
| A statechart of a feature's states | A model of the feature's states that **statechart** checks against its rules | Attached to the reply whenever a change touches that feature's states |
| The decision trail of a long run | The run itself, through **show-me-your-work** | Written as the run goes |

## What the starter adds

When grill is done, `grill/scripts/starter.mjs` writes what the project lacks. It never overwrites a file, so running it again is safe.

| File | What it does |
| --- | --- |
| `.github/workflows/ci.yml` | Runs the project's one check command on every pull request and on main. Until that command is set, the step fails and says so |
| `.githooks/pre-commit` | Before each commit, the quality floor of **constraint-driven-development** and a gitleaks secret scan. The starter enables it in the clone and keeps the floor guard in the clone's git folder, outside the tree |
| `AGENTS.md`, and `CLAUDE.md` holding `@AGENTS.md` | The skeleton of the project's instructions for agents. The agent fills it from grill's decisions and leaves "to confirm" where nothing was settled |

## What is retired

| Old document | Replaced by |
| --- | --- |
| A hand-written requirements document (PRD) | The feature files, `GLOSSARY.md`, `CONSTRAINTS.md`, and `docs/rulings.md`, summarized by the generated overview |
| `docs/architecture.md` | **architect**'s design, settled before code, plus ADRs for the choices that need one |
| `docs/TEST_PLAN.md` | Each feature's Done when list, the project's verification skill (made by **create-verification-skill**), and the checks in `CONSTRAINTS.md` |
| `TODO.md` as the status of record | The ticked and open Done when items, counted in the overview; within a long run, the playbook's todo list and decision trail |

An existing project that already keeps one of these files may go on keeping it, but it must not hold a fact that a source also holds. Point to the source instead.

## Scope: grill's questions

Before a new project or an unclear large feature, **grill** asks only what a person can answer. Every question comes with a recommended answer and a default, so "I don't know" still gives a working decision.

| Ask | To learn |
| --- | --- |
| What | The first version's features, and what is out of scope (for example login, payments, sending anything automatically) |
| For whom | Who uses it, in which roles, to get which task done |
| Done | What you would see that tells you it works, including what should happen when something fails |
| Wrong | What would make you call it broken, unsafe, too slow, or too expensive |

Where the first version ends is part of "done": something to show, something you use yourself, something others try, or something public. The answers differ for each, so it is settled first.

Technical questions (data shapes, modules, libraries) are not asked; they are listed in the feature file for **architect**. A question that only trying something can answer goes to a **prototype**.

## Follow-up branches

When a project has one of these, **grill** asks the matching follow-up, and the answer lands in a feature file's Done when list or as a row in `CONSTRAINTS.md`.

| When the project has | grill asks about | Lands in |
| --- | --- | --- |
| Screens or several steps | Empty, loading, and failure states along the main flow | Done when items |
| Saved data | What is kept, how it changes, how it is deleted and recovered | Done when items; an ADR for the storage choice |
| Parts built separately (front and back end, modules) | What each side may assume about the other | Done when items; a CONSTRAINTS row for contract tests |
| Logins, roles, private data, or uploads | Who may see what, where secrets live, what is logged | Done when items; CONSTRAINTS rows for secrets and dependency scanning |
| AI answers, recognition, or ranking | Sample inputs, what counts as right, the quality bar, cost, speed | An eval set; CONSTRAINTS rows for its pass rate and budget |
| AI drawing on documents | Which sources, which version wins in a conflict, how answers cite them | Done when items |
| Automatic messages, scheduled jobs, or calls with side effects | Repeats, retries, when to stop, who may approve | Done when items; actions that cannot be undone still pause for a person |
| A service that must stay up | Deploy, health checks, rollback, backups | Done when items; CONSTRAINTS rows that run before release |
| Payments or subscriptions | Order states, duplicate callbacks, refunds, a test mode | Done when items |
| Several platforms, browsers, or devices | Which ones, which versions | A CONSTRAINTS row for the test matrix |
| A core capability nobody knows is possible | The smallest experiment that would answer it | A throwaway experiment on its own branch; the verdict in an ADR or `docs/rulings.md` |

## Writing rules

These hold for every document, generated or not.

**Truthfulness**

- Keep plans and results apart. A plan says how something will be checked; a result says what was actually run, whether it passed, and what was not checked. Nothing is written as passed without a real run behind it.
- Mark a judgment nobody has tested as untested, and never write a guess as a fact.
- Write absolute dates (2026-10-20), never "yesterday" or "next week".

**Readers and structure**

- Write for a reader who is not an engineer and for the agent. Plain words; explain a technical term the first time it appears.
- Lead with the conclusion, then the reasons. Compare options in a table with their cost and why one was chosen.
- One document, one job. State a fact once, in its source, and link to it elsewhere.
- Be specific. "Supports questions about the docs" is too vague to check; "answers questions the docs cover, with a link to the passage, and says to ask a person when they do not" becomes Done when items as written.

**Links and paths**

- Link project documents with relative paths. Never write a path on your own machine into a project document; it breaks when the project moves.

**Several agents**

- `AGENTS.md` is the only rules file. Other harnesses' files (such as `CLAUDE.md`) only point to it.
- An agent taking over reads `AGENTS.md` and the overview first, then checks the code, versions, and check results against them. Nothing that must last lives only in one agent's memory: decisions go into the sources.
- Keep the documents neutral about which agent does what, unless you have split the work that way.

## When things change

| Change | Update |
| --- | --- |
| A new feature, or a changed flow or finish line | Its feature file (and the overview, regenerated) |
| A new term, or a term used two ways | `GLOSSARY.md` |
| A changed quality bar | `CONSTRAINTS.md`. An agent may tighten it; the merge gate's floor refuses a change that loosens it, so loosening is yours to do and merge yourself |
| A hard-to-reverse technical choice | A new ADR; the old one marked superseded |
| A decision you made in conversation | `docs/rulings.md`, your words and the date |
| A changed way to start, configure, or release | `README.md` |
| A changed step a person takes | The user guide |

A document that is out of date is either fixed or marked at the top as replaced by its successor, so two versions never disagree. You decide the requirements and the trade-offs; agents may draft them, and every claim that something works rests on a run.
